# Revisão do projeto — 13/10/2026

Revisão de tudo que foi montado até aqui (instalação do REA, gate, protocolos, guia, pilha de games) e busca por abordagens mais eficientes.

## 1. O que a pesquisa trouxe

| Achado | Uso no projeto |
|---|---|
| **MDA** (Mecânicas–Dinâmicas–Estética, Hunicke/LeBlanc/Zubek) é o framework padrão para analisar mecânicas e dinâmicas | Espinha do novo `protocolo-mecanicas` e do modelo `03-mecanicas.md` |
| **Dados antes de código:** valores de balanceamento ficam em assets — Unity (ScriptableObjects, via UnityPy/AssetRipper) e Unreal (DataTables/CurveTables, via FModel/CUE4Parse → JSON) | Camada "dados" acrescentada ao plano de integração; passo 2 do protocolo |
| **Fontes da comunidade** já documentam mecânicas em detalhe: TASVideos (física, RNG, frame data), TCRF, wikis, speedrun | Passo 1 do protocolo (hipóteses baratas, confirmadas depois no alvo) |
| **Dinâmicas por simulação:** Machinations é o padrão comercial (SaaS), mas simulação local com semente fixa resolve e não envia dados para fora | Passo 5 do protocolo (`registros/<slug>/simulacoes/`) |
| **Método do oráculo** (já no universal-modder): prever pela fórmula e comparar com o jogo real | Passo 4 do protocolo |
| Nenhuma ferramenta pronta faz o pipeline "jogo → documento de mecânicas" | O protocolo cobre essa lacuna combinando REA + ferramentas da pilha |

## 2. Aplicado nesta revisão

1. **Recurso de mecânicas e dinâmicas:** skill `protocolo-mecanicas` + modelo `registros/_modelos/03-mecanicas.md` + passo novo no fluxo do `CLAUDE.md`.
2. **Regra de repositório público:** `registros/` não leva assets extraídos, dados brutos nem código descompilado extenso (risco real, porque o repositório é público e a análise de jogos gera esse material).
3. **Camada de dados e fontes da comunidade** no `docs/plano-integracao-games.md`.

## 3. Propostas (precisam de decisão)

| # | Problema | Proposta | Custo | Mexe em |
|---|---|---|---|---|
| P1 | O gate só cobre `mcp__rea__*`; o GhidraMCP ficaria sem trava | Generalizar o hook para vários servidores (um mapa por servidor) **antes** de registrar o GhidraMCP | Médio | `.claude/hooks/` (projeto) |
| P2 | `npx rea <comando>` contra um alvo escapa do gate (só regra escrita) | Hook `PreToolUse` de Bash que pede confirmação para subcomandos do REA que recebem alvo; os sem alvo (`--help`, `doctor`, `providers`, `capabilities`, `mcp doctor`) passam | Baixo | `.claude/settings.json` + hook (projeto) |
| P3 | A regra de repositório público depende de disciplina | Checagem antes do commit em `registros/`: bloquear binários, arquivos de dados grandes e blocos de código longos | Baixo | hook de git do projeto |
| P4 | O GateGuard (plugin ECC) exige declarar fatos antes de cada arquivo novo e do primeiro Bash, o que atrasa | Desligar só a parte de edição/escrita neste projeto (`ECC_DISABLED_HOOKS=pre:edit-write:gateguard-fact-force`), mantendo a de Bash | Baixo | `.claude/settings.json` (projeto) |
| P5 | A tarefa mensal só revisa o guia do REA; o comparativo de ferramentas envelhece rápido (o ecossistema MCP muda toda semana) e os clones em `ferramentas/` ficam parados | Estender a tarefa mensal: atualizar números do `benchmark-ferramentas-re.md` e avisar se os clones fixados ficaram para trás | Baixo | `~/.claude/scheduled-tasks/` |
| P6 | API do GitHub sem autenticação (60 req/h) travou a pesquisa | Instalar o GitHub CLI (`winget install GitHub.cli` + `gh auth login`); também destrava o @devops | Baixo | sistema |

## 4. O que continua como está

- REA 6.4.0 fixado e auditado; gate fail-closed; protocolos de segurança e benchmark.
- Pilha de games instalada por alvo, cada ferramenta auditada e fixada.
- Pendências da camada nativa no `docs/runbook-prereqs-nativo.md` (JDK 21, Ghidra 12.1.4, GhidraMCP 2.0).
